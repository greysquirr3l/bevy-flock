# What 1.0 means here

This is the line in the sand. Everything below has to be true before the version number earns a `1.0`, and the phase 6
restructure is judged against it rather than the other way round. It is a gate list, not a wish list: each item says what
"done" means, how it can be checked, and what is missing today.

The goal is not to win a benchmark. It is to be a crowd engine a stranger can adopt on a Tuesday, and still be using when
the version number becomes 2.0.

> The executable version of this page is [`release-checklist-1.0.md`](release-checklist-1.0.md): nine steps, the command
> for each, and the state of each written down. The 0.1.0 crowd milestone keeps its own sign-off in
> [`release-checklist.md`](release-checklist.md).

## 1. The public surface is frozen and documented

**Done means:** every `pub` item in the facade paths, `bevy_flock::application`, `::domain`, `::adapters::primary`, is
either documented with a runnable example or deliberately hidden. No public type exposes an internal one. The phase 6
core-crate split preserves these paths exactly; a game that compiled against 1.0-rc compiles against 1.0.

**Check:** `cargo doc --no-deps --all-features` with `#![deny(missing_docs)]`; a compile-only test crate that uses the
documented paths and nothing else.

**Today:** the crate has strong internal docs and ADRs, but no inventory of what is *promised*. Phase 6's
`headless-consumer-gate` task is the mechanism that will prove the facade compiles without the engine.

## 2. Semver and an MSRV that is a promise, not a coincidence

**Done means:** `rust-version` in the manifest is the tested floor, CI builds on exactly that toolchain, and the README
says so. The changelog states what counts as a breaking change for this crate specifically, for a simulation, that
includes a *behaviour* change that alters deterministic output, even when the type signatures are identical.

**Check:** a CI job on the declared MSRV; a changelog entry for every public change.

**Today:** `rust-version = "1.97.1"` and `rust-toolchain.toml` exist; the policy sentence for behavioural breakage does
not.

## 3. A stranger can be running a crowd in five minutes

**Done means:** the README's first code block spawns a population, ticks it and reads a result, with no feature flags, no
asset files and no Bevy app boilerplate that the crate could supply. `hello_flock.rs` exists as the honest version of
this; the README has to lead with it rather than with architecture.

**Check:** time a fresh checkout to a running example, on a machine with nothing cached.

## 4. Errors are typed for a caller, not a log

**Done means:** every fallible entry point returns a typed error that names the failing field and the value, and the
variants a game can actually act on are documented as such. No `Result<_, String>`, no panics on user input, no
`unwrap` in a path a caller can reach.

**Check:** the config error tests exist already (`ConfigError::InvalidDistance { field, value }` is the pattern); the gate
is that no public function panics in its documented preconditions.

## 5. The guarantees are stated where an adopter will read them

**Done means:** one page listing what the crate promises, deterministic output for a seed, byte-identical spatial windows
across worker counts, zero steady-frame allocation on the steady path, and the budgets it holds at 1k/10k/100k/1M, each
with the test that enforces it. A guarantee without a test is a slogan.

**Check:** every claim in that page links to a test name.

**Today:** the properties are enforced (the parity matrix, the allocation counters) but scattered across ADRs and
`docs/dev/tuning/performance.md`. The page is the deliverable.

## 6. Phase 6: the simulation core is separable

**Done means:** the ECS-free core compiles alone (`bevy-flock-core`), the facade re-exports the same paths, a headless
consumer runs a crowd with no Bevy app at all, and `tests/core_boundary.rs` still forbids engine dependencies in the core
layers. This is what makes the crate useful to a server or a test harness, and it is the last structural change before
1.0, after 1.0, moving modules becomes a semver event.

**Check:** the `headless-consumer-gate` task, plus the existing boundary test.

## 7. Performance claims are comparable, not decorative

**Done means:** `docs/dev/tuning/benchmarks/cross-engine.md` has rows for Godot and Unreal on **one machine**, produced by
the harnesses in `benchmarks/`, with the comparison generated by `scripts/compare_benchmarks.py` rather than typed by
hand.

**Today:** all three rows exist from one host. A 2026-11-09 run on an Apple M3 Pro with 11 threads produced bevy-flock
0.1.0, Unreal 5.8.2 and Godot 4.7.2 rows at 10,000 and 100,000 agents, 1,000 measured ticks each; the table is in
`benchmarks/README.md`. Unreal took 0.937 and 3.496 ms, we took 2.217 and 16.528 ms, Godot's grid took 4.674 and
38.054 ms, and 47.8% of our 100,000-agent ticks missed the 16.6 ms budget.

Two caveats are load-bearing, and both travel with the numbers. Unreal's row is a `UTickableWorldSubsystem` running a
hand-written SoA loop, not Mass Entity, so it compares against a competent subsystem rather than against Unreal's crowd
stack. Our row steers every agent: `FlockPlugin` installs the memory bridge and `BoidsPlugin`, not the manifest band, so
the 100,000 number is the no-culling case and not the 5,000-manifested banded case.

What is not yet met is the *mechanism*. That run assembled its table by hand, because the Bevy harness read
`/proc/cpuinfo` on macOS and reported `unknown cpu` while the Godot row on the same laptop said `Apple M3 Pro`, which is
exactly what `scripts/compare_benchmarks.py` refuses to put in one table. The harness now names the CPU on all three
platforms, so what remains is one real set merged through the comparator.

The earlier two-engine run stays recorded in `cross-engine.md` as a different machine, and its rows do not divide into
the laptop's: on a six-core aarch64 VM, bevy-flock was 2.5x faster than a GDScript loop that rebuilds a grid each tick,
and 1.9x at 10k / 1.5x at 100k slower than a GDScript loop that does no indexing at all. The second row is the price of
the work we do that it does not, and it is the honest way to state the first.

The first of the measurements that would tighten the laptop comparison now exists, and it has run on the laptop:
`--workload all` runs the Unreal fixture's loop twice, bare and inside one ECS system, with the two rows bit-identical by
test. On the M3 Pro the ECS and its schedule cost 0.05% of the plugin row at 10,000 agents and nothing above noise at
100,000; the matched loop is 2.2x and 2.0x faster than Unreal's loop on the same host; and the plugin's own work is 5.1x
and 9.2x the loop, which is 80.3% and 89.1% of the product row and the whole of the 4.6x gap at 100,000. So the gap is
this crate's workload, not the engine around it, and the sandbox's earlier suggestion that the loop itself was behind was
an artefact of comparing a memory-bound single-threaded row across two hosts. The worker question is answered for the build and open for the frame: pinning the grid rebuild to 1, 2, 4 or 6
workers moves the 100,000-agent row by under 1%, because the build is 0.97 ms of it at six threads and 1.79 ms at one,
while the steering pass reads its threads from the compute task pool and ignores the flag. The frame scales with the pool and not with the grid: `--pool 1,2,4,6` measures 2.83x on six threads at 100,000
agents and 2.19x at 10,000, while `--workers` moves the row by under 1%. What is left of the attribution is instrumented
counts of scanned cells and neighbours, and the headless render-plan cost.

## 8. Release mechanics that do not depend on the author's memory

**Done means:** a tag builds and publishes by script; `cargo publish --dry-run` is clean with every feature combination;
`cargo-deny` passes; the changelog is generated from commits or written at the tag; `SECURITY.md` says how to report a
bug and what support window a 1.x has.

**Today:** `RELEASING.md`, `deny.toml` and the changelog habit exist, this item is mostly verification.

## What is explicitly *not* a 1.0 requirement

- More speed. Phase 5 closed at 6.289 → 4.572 ms for a 1M-body rebuild, with two proposed optimisations measured and
  rejected. That is the answer; the next millisecond is a 1.x patch if a user needs it.

- Rendering, physics, networking or file adapters. The crate simulates. `README.md` says so and will keep saying so.
- A visual editor, a scripting language, or a node graph. Pluggable behaviour is the extension point.

## The order

1. Write items 1–5 as documents and checks (this file is item 0: the list).
2. Run phase 6 against item 6, which is the only structural change left.
3. Produce item 7's table on one machine.
4. Freeze: tag `1.0.0-rc1`, hold it for a release cycle, then `1.0.0`.

Item 6 comes before the rest of the freeze precisely because it moves modules, and after 1.0 that is no longer allowed.
