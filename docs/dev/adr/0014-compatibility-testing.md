# 0014, Save compatibility is tested against committed files and a pinned old build

- Status: Accepted
- Layer 4 landed at `v0.1.0-rc.1`; see "The pinned build, as built" below
- Date: 2026-11-04
- Relates to: ADR 0012 (format version 1), ADR 0013 (version 2 and the registry)

## Context

ADR 0012 promised that "version 1 must be loadable forever", and ADR 0013 added a
second version, a migration policy and a section table built so a *third* version
should not be needed. Both records describe behaviour; neither describes how the
promise is checked, and the ordinary test suite cannot check it:

- Unit tests build the reader and the writer from the same source tree, so they
  agree with each other by construction. A writer that quietly changes a field
  width will still round-trip against its own reader, on the day it is written, in
  the one build that contains both.
- The failure a player experiences is *old file, new build*. Nothing in a
  single-commit test run models "new build".
- The failure a modder experiences is *new file, old build*: a save written by a
  newer release, opened by the copy of the game they have installed. That direction
  is not testable with one binary at all, it needs an old one.

So the promise needs a corpus that outlives the build, and a second binary that is
deliberately not current. This record fixes both, plus the two edge directions that
are cheap to fabricate: a file from the future, and a file that has been corrupted.

## Decision

**Four layers, each catching a failure the others cannot.**

### 1. A committed corpus of golden files

```text
tests/fixtures/
  manifest.toml          # what each file is, who wrote it, its digest
  v1/basic.bflk          # 2 NPCs, 1 subject, one grudge
  v1/archive.bflk        # an archived relationship, for the retention path
  v1/empty.bflk          # a header with no records: 32 bytes
  v2/basic.bflk          # the same world, with a registry
  v2/relabelled.bflk     # same keys, different labels: must load identically
  v2/unknown_section.bflk# a section id this build does not implement
  v2/future_version.bflk # header says 3: must be refused, not guessed
```

The files are binary, small, and **never regenerated by CI**. Every fixture is
committed with the digest of its own bytes, so a test that loads it is testing bytes
that no current code path can have produced during that run. That is the entire
point: a reader that only agrees with its sibling writer proves nothing about the
files already on players' disks.

Each fixture is declared in `manifest.toml` with its expected *summary*, record
count, slot count, and the digest of the decoded store, not its expected bytes. A
version 2 writer may legitimately emit identical bytes for identical input (it
does, and layer 2 checks that), but a version 1 reader path must not be held to a
byte match with a writer that no longer exists.

### 2. A format freeze test with an explicit blessing step

One canonical world is encoded and compared byte-for-byte with a committed file:

```text
assert_eq!(canonical_world().to_bytes(), include_bytes!("fixtures/v2/canonical.bflk"))
```

This catches the writer drift the round-trip tests cannot: a reordered field, a
changed default, a new section, a different checksum region. When the format changes
*intentionally*, the test fails and the developer re-blesses:

```text
BLESS_SAVES=1 cargo test --test save_compat
```

Blessing rewrites the fixture, and the diff appears in the pull request as a binary
change next to the ADR that authorised it. Two things are thereby enforced: a format
change cannot be accidental, and it cannot be undocumented.

### 3. A compatibility matrix, including a real old build

| Reader | File | Expectation |
| --- | --- | --- |
| current | `v1/*` | loads under `AssumeDense`, reports `unverified_mapping` |
| current | `v2/*` | loads, registry translated by key |
| current | `v2/unknown_section` | loads, section skipped |
| current | `v2/future_version` | `UnsupportedVersion`, refuses |
| current | every fixture, byte-flipped | typed error, never a panic |
| **pinned old build** | `v2/*` | either loads or refuses *by name*, never panics |
| pinned old build | `v1/*` | loads identically to that build's own tests |

The pinned build is a second workspace member:

```toml
# compat/Cargo.toml
[dependencies]
bevy-flock = { path = "..", package = "bevy-flock", optional = true }
# and, for the real check, the last released tag:
# bevy-flock = { git = "…", tag = "v0.1.0" }
```

CI compiles `compat` against the *last released tag* and runs it over the fixture
corpus. This is the only way to test the direction that actually breaks players,
and it costs one small crate and a pinned revision.

The rule for the pinned build is deliberately weaker than for the current one: an
old build may not understand a new file, so it is allowed to refuse. What it is not
allowed to do is panic, mis-attribute subjects, or accept a file it does not
understand by guessing. Refusal is a compatibility outcome; silent misreading is not.

### 4. Mutation fuzzing for the error surface

Every byte of a valid fixture is flipped, and every prefix length is tried:

```text
for index in 0..bytes.len()   { assert typed error or Ok }
for cut   in 0..bytes.len()   { assert typed error or Ok }
```

with a fixed seed and a bounded budget so CI stays deterministic. The assertion is
not "the load fails", some mutations land in a label and are legal, but "the load
either succeeds or returns a `SaveError`, and never panics, never allocates more
than the header claims, and never returns a store that disagrees with the file's
own checksums".

This is the layer that pays for `ImplausibleCount` existing: a file claiming four
billion records must be rejected before the `Vec::with_capacity` that would try to
allocate them.

## The pinned build, as built

`compat/` is its own workspace with one dependency:

```toml
bevy-flock = { git = "https://github.com/greysquirr3l/bevy-flock", tag = "v0.1.0-rc.1", features = ["memory"] }
```

A path dependency would defeat the entire exercise, so the pin is a tag and CI rebuilds
against it. Run over the committed corpus, the released build reports:

```text
v1/basic.bflk              LoadsUntrusted  decoded, and untrusted restore refused: MissingSubjectRegistry { version: 1 }
v2/canonical.bflk          Loads           decoded and restored: 2 store records, 1 archived
v2 with version 99         RefusesVersion  refused by number: version 99
v2 with one flipped bit    Decides         refused with a typed error: ChecksumMismatch { section: "registry" }
```

Four cases, three verdicts a released build is allowed: it loads what it understands,
refuses what it does not *by name*, and never panics. The fourth case, a forged
version, is the one that matters most, because the tempting implementation is to read
the fields it recognises and hope.

The harness synthesises its future files rather than committing them, which is the one
place this record departs from "commit the bytes": a file from the future has no writer
to preserve it, and a committed forgery would have to be regenerated every time the
version number moved.

## What this framework does not test

- **Game content.** A registry key is the game's; the framework cannot know whether
  reusing one was a mistake. That obligation is documented on `SubjectKey` and is
  the game's to keep.
- **Big-endian hosts.** The format writes little-endian explicitly, so it is
  endianness-independent *by construction*; running the corpus on a big-endian host
  would test the compiler, not the format. The construction is reviewed instead.
- **Files from a build that was never released.** A fixture is blessed at release
  time; anything on `main` that is not in a tag is fair game to change.

## Consequences

- **A fixture that fails to load is a P0, and the fix is the reader.** Never the
  fixture, regenerating a broken fixture deletes the evidence and the promise with
  it.
- **The corpus grows by one small file per behaviour, not per release.** Eight files
  today; a version 3 adds a directory, not a matrix.
- **`BLESS_SAVES=1` is a footgun with a bright label.** It rewrites committed bytes;
  the mitigation is that the diff is binary and reviewable, and that the manifest
  records which build produced each file.
- **The pinned build turns red on purpose.** When an old build's expectation is
  genuinely obsolete, the fix is to retire that pin with an ADR note, not to delete
  the test.
- **Fuzzing costs a few seconds in CI**, bounded by fixture size × 8 bits per byte.
  With a 200-byte fixture that is 1,600 loads; with a 2 MB file it would be 16
  million, which is why the corpus is deliberately small and the 50,000-NPC file
  lives in `benches/` instead.

## Alternatives rejected

- **Round-trip tests only.** The status quo, and it cannot fail in the direction
  that matters: it is one build agreeing with itself.
- **Generate fixtures at test time.** Cheap, and it tests nothing: the generator is
  the writer.
- **Snapshot the decoded `Debug` output.** Ties the fixture to a struct's formatting
  and fails on a field rename that harms nobody.
- **A separate repository for the corpus.** Splits the format change from the format
  test across two pull requests, which is how a format change lands without its
  fixture.
- **Semantic-version the format instead of file versions.** A save file does not
  carry a crate version, and the crate version does not tell a reader which fields
  exist.
- **Test forward compatibility by shipping the previous binary in CI artifacts.**
  Needs an artifact pipeline to test something a pinned dependency tests in four
  lines.
